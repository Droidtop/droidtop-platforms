# plugins/ — what the enginehost plugin repositories have published

`index.json` is one file describing every registered plugin repository's
releases: per repository its origin, its trust level, its signing key, and
per release its tag, stream, publication time and assets (name, download URL,
size, sha256). Enginehost reads it from `raw.githubusercontent.com`, which
has no API allowance, **before** it asks GitHub's API anything.

The reason is arithmetic. GitHub's unauthenticated API allows 60 requests an
hour per address. Enginehost listing the plugin repositories itself costs one
API request per origin plus a download per release, so a few refreshes from
one address — a fresh emulator instance, a shared connection — spent the
allowance, and the catalog screen then showed "Nothing published yet" with no
reason. Now the listing happens once here, in a workflow with a token, and
every device reads the result.

This is a snapshot, and enginehost treats it as one:

- an origin the index does not name (any repository a person added
  themselves by URL) takes the GitHub API path, with the ETag enginehost
  stored for it, exactly as before;
- an index older than three days is ignored entirely and every origin takes
  that path;
- nothing here is trusted on its own. The release envelope is fetched and
  checked against the `sha256` published here, and the signed manifest inside
  it is verified against the key pinned for that origin, before a single
  build appears on screen. The index can make the catalog fast or stale; it
  cannot make it lie.

## The files

| File | Written by | What it is |
| --- | --- | --- |
| `index.json` | the workflow | What every registered repository has published, verified. Never hand-edit. |
| `origins.json` | the workflow | The registered repositories and the key fingerprint each is pinned to. A repository gets in by validating (below), not by an edit. Removing a line by hand deregisters it. |
| `third-party.json` | a reviewed pull request | The third-party maintainers allowed to register repositories, their GitHub accounts, their keys and their repositories. |
| `official-root-key.json` | a reviewed pull request | The public half of the offline Enginehost root key, the same file Enginehost compiles in (`app/src/main/res/raw/official_plugin_root_key.json`). |

Everything in `index.json` and `origins.json` is generated by
`generator/plugins_index.py`, which the `Plugins index` workflow runs on a
schedule (every six hours), on `workflow_dispatch`, on a `repository_dispatch`
of type `plugin-published`, and on a registration issue. A push that touches
these files runs it with `--check`, which validates them against each other
without spending any API calls.

## How a repository gets in (and stays in)

A repository announcing itself is a **hint**. The generator never takes
anything from the announcement except which repository to look at; what
enters the index is what it verified from that repository's own releases:

1. **The key.** The repository's `enginehost-public-key.json` (from its
   releases, or its tree) must name the repository as its origin and be an
   ECDSA P-256 key whose fingerprint matches. For a Droidtop repository the
   key must carry the Enginehost root's certificate for exactly that origin;
   for a third party it must be a key their list entry names. Once
   registered, the fingerprint is pinned in `origins.json`: a release signed
   by any other key is left out and the run carries a warning.
2. **Every bundle's signed manifest.** Each bundle in each release envelope
   must name the repository as its origin, embed the pinned key, and verify
   against it; its archive must be one of the release's assets. A release
   with a bundle that fails is left out.
3. **Both ABIs.** A bundle that carries native libraries must carry
   `arm64-v8a` and `x86_64` (Enginehost `docs/engine-bundle-format.md`). This
   is checked when a release is admitted: a release already in the index
   with the same tag and the same envelope stays, so builds devices already
   run do not disappear, and the next publish of that tag must carry both.
4. **Third parties only:** the repository must publish a registration signed
   by its maintainer's listed key (below), and no bundle ID may be in the
   official `dev.enginehost.*` namespace.

A Droidtop repository that validates and is not in `origins.json` yet is
registered by that run — a new plugin repository is in the catalog the first
time it publishes and announces, and on devices as soon as they refresh
(Enginehost adds any origin whose key the root certified; see its
`docs/plugin-catalog.md`). A registered Droidtop repository that stops
validating keeps its registration and pin but is left out of the index, so
devices ask GitHub for it directly and verify it themselves.

## The step each Droidtop plugin repository runs

Every Droidtop plugin repository ends **both** its `publish` and `unstable`
jobs with this step, on every branch that builds (`plugin-core` carries it as
the template the lines merge from):

```yaml
      - name: Ask droidtop-platforms to reindex
        env:
          # Enginehost reads droidtop-platforms' plugins/index.json before it
          # asks GitHub's API anything, so a release is only offered once that
          # index knows about it. A cross-repository dispatch needs a token of
          # its own; this job's GITHUB_TOKEN cannot reach another repository.
          # Without the secret this is a no-op and the index's scheduled run
          # picks the release up within hours. See droidtop-platforms
          # plugins/README.md.
          GH_TOKEN: ${{ secrets.PLATFORMS_DISPATCH_TOKEN }}
          GH_REPO: ${{ github.repository }}
        run: |
          set -euo pipefail
          if [ -z "${GH_TOKEN:-}" ]; then
            echo "No PLATFORMS_DISPATCH_TOKEN; the plugins index picks this release up on its schedule."
            exit 0
          fi
          gh api repos/Droidtop/droidtop-platforms/dispatches \
            -f event_type=plugin-published \
            -f "client_payload[repo]=$GH_REPO"
```

`PLATFORMS_DISPATCH_TOKEN` is one organisation secret — a fine-grained token
with `contents: write` on `Droidtop/droidtop-platforms` and nothing else (a
repository dispatch needs write on its target) — made available to the
plugin repositories. Until it exists every repository falls through to the
scheduled run, which is why the step is written to succeed without it. What
its holder could do, and why that is bounded, is in Enginehost's
`docs/security/2026-09-25-third-party-catalog.md` (T1, T2).

## Third-party repositories

Anyone can publish an Enginehost plugin repository, and anyone can add one to
their own Enginehost by URL. `third-party.json` exists so a person does not
have to find the URL: Enginehost's Plugins screen offers every registered
third-party repository under **Quick add third-party repositories**, one tap
each, behind a prompt that shows the maintainer and the key fingerprint.
Their bundles are marked **Third party** everywhere Enginehost shows trust;
they are never Official, and every one of them still waits for the person's
approval before it runs. Listing is identity, not code review.

### Getting listed

Open a pull request adding your entry to `third-party.json`:

```json
{
 "id": "example",
 "name": "Example Person",
 "github": "example-person",
 "keys": [
  {
   "algorithm": "SHA256withECDSA",
   "publicKeySpki": "BASE64 DER SubjectPublicKeyInfo of your P-256 key",
   "keySha256": "SHA-256 of that DER, upper-case hex"
  }
 ],
 "repos": ["example-person/enginehost-example-plugin"]
}
```

- `id`: lowercase letters, digits and dashes, unique. Neither `id` nor
  `name` may contain "droidtop" or "enginehost".
- `github`: your GitHub login. Registration issues are acted on only when
  opened from this account.
- `keys`: the key(s) your bundles and your registration are signed with.
  Adding a key is how you rotate; devices that pinned your old key keep
  refusing new releases until their owner removes and re-adds you.
- `repos`: `owner/name`, never a `Droidtop/` repository.

The generator's `--check` validates the entry on the pull request's push.
Removing an entry deregisters its repositories on the next run.

### Registering a listed repository

Your repository needs three things, and never any Droidtop token:

1. `enginehost-public-key.json` on its `plugin-core`, `main` or `master`
   branch (Enginehost reads it from there when a person adds you, and refuses
   if it disagrees with the key listed here) and attached to your releases,
   in the format of Enginehost's `docs/plugin-catalog.md`.
2. Releases in Enginehost's format (`docs/engine-bundle-format.md`,
   `docs/plugin-catalog.md`), signed with that key, carrying both ABIs, with
   bundle IDs outside `dev.enginehost.*`.
3. `enginehost-registration.json` on the same branch, signed with the same
   key:

   ```json
   {
    "formatVersion": 1,
    "origin": "https://github.com/example-person/enginehost-example-plugin",
    "maintainer": "example",
    "keySha256": "THE KEY'S FINGERPRINT",
    "signatureBase64": "..."
   }
   ```

   The signature is `SHA256withECDSA` over these four lines, each ending in
   a newline, with the origin in lower case:

   ```sh
   printf 'enginehost-registration-v1\n%s\n%s\n%s\n' \
     https://github.com/example-person/enginehost-example-plugin example "$FINGERPRINT" \
     | openssl dgst -sha256 -sign your-key.pem | base64 -w0
   ```

The scheduled run looks at every listed repository, so that is all. To be
picked up now rather than within six hours, open a **Register a third-party
plugin repository** issue here from your listed account; the workflow runs,
answers in the issue with what it registered or refused, and closes it.
Deleting the registration file deregisters the repository on the next run.
