# plugins/ — what the enginehost plugin repositories have published

`index.json` is one file describing every default plugin origin's releases:
per origin the repository, and per release its tag, stream, publication time
and assets (name, download URL, size, sha256). Enginehost reads it from
`raw.githubusercontent.com`, which has no API allowance, **before** it asks
GitHub's API anything.

The reason is arithmetic. GitHub's unauthenticated API allows 60 requests an
hour per address. Enginehost listing the eleven plugin repositories itself
costs one API request per origin plus a download per release, so a few
refreshes from one address — a fresh emulator instance, a shared connection —
spent the allowance, and the catalog screen then showed "Nothing published
yet" with no reason. Now the listing happens once here, in a workflow with a
token, and every device reads the result.

This is a snapshot, and enginehost treats it as one:

- an origin the index does not name (any repository a person added
  themselves) takes the GitHub API path, with the ETag enginehost stored for
  it, exactly as before;
- an index older than three days is ignored entirely and every origin takes
  that path;
- nothing here is trusted on its own. The release envelope is fetched and
  checked against the `sha256` published here, and the signed manifest inside
  it is verified against the key pinned for that origin, before a single
  build appears on screen. The index can make the catalog fast or stale; it
  cannot make it lie.

`origins.json` is the list the index covers. It IS enginehost's
`PluginOriginStore.DEFAULT_ORIGINS`: a repository added there is added here.

Everything in `index.json` is generated by `generator/plugins_index.py`,
which the `Plugins index` workflow runs on a schedule (every six hours), on
`workflow_dispatch`, and on a `repository_dispatch` of type
`plugin-published`. Do not hand-edit it. A push that only touches these files
runs the generator with `--check`, which validates the committed index
against `origins.json` without spending any API calls.

## The step each plugin repository adds

A release is in the index within hours anyway, but a repository that tells
this one it published gets there in a minute. Add this as the last step of
**both** the `publish` and the `unstable` jobs in that repository's
`.github/workflows/android-plugin.yml` — it is already in
`Droidtop/enginehost-renpy-plugin`, which is the template:

```yaml
      - name: Ask droidtop-platforms to reindex
        env:
          # A cross-repository dispatch needs a token of its own; the job's
          # GITHUB_TOKEN cannot reach another repository. Without the secret
          # this is a no-op and the scheduled run picks the release up.
          GH_TOKEN: ${{ secrets.PLATFORMS_DISPATCH_TOKEN }}
        run: |
          set -euo pipefail
          if [ -z "${GH_TOKEN:-}" ]; then
            echo "No PLATFORMS_DISPATCH_TOKEN; the plugins index picks this release up on its schedule."
            exit 0
          fi
          gh api repos/Droidtop/droidtop-platforms/dispatches \
            -f event_type=plugin-published \
            -f 'client_payload[repo]=${{ github.repository }}'
```

`PLATFORMS_DISPATCH_TOKEN` is one organisation secret — a fine-grained token
with `contents: write` on `Droidtop/droidtop-platforms` and nothing else —
made available to the plugin repositories. Until it exists, every repository
including the template falls through to the scheduled run, which is why the
step is written to succeed without it.
